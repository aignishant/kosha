# 5.2 — The editor, the pager, and a diff you can actually read

> **One-line answer.** Git regularly hands control to two other programs — an editor when it needs
> prose from you, a pager when it has more output than a screen — and configuring both is the
> difference between a tool that feels hostile and one that feels like yours.

---

## The story

Somebody's first week, and the first commit that is not made with a one-line message.

They type the command without `-m`, and the screen changes. Not a prompt, not a dialogue box: the
whole terminal is replaced by something with a strip along the bottom and a cursor that does not move
when they type. Letters do not appear. Pressing keys produces beeps, or worse, nothing.

They try Ctrl-C. Something happens; the screen stays. They try typing "no", and the machine does
something with the "n". Eventually they close the terminal window, which does work, in the sense that
a hammer works.

The thing on the screen was an editor that has been on Unix systems since the seventies and expects
you to know that you are in command mode. Nobody had ever mentioned it. And the reason it appeared —
that a commit message is *prose*, and prose is written in an editor, so Git launches the one your
system nominated — is completely reasonable and completely invisible from inside the panic.

The second program is like the first. A long log fills the screen, the prompt does not come back, and
the keyboard seems dead. That one is a pager, and the way out is one letter.

Nobody should meet either of these for the first time during real work.

---

## The idea in plain language

Git delegates two jobs it has no business doing itself.

**An editor**, when it needs text from you that is longer than a command line: a commit message
without `-m`, a tag annotation, the todo list of an interactive rebase (Day 60), a merge message. Git
writes a file, launches your editor on it, and waits. When the editor exits, Git reads the file back
and looks at the exit status.

**A pager**, when output might be longer than the screen: `git log`, `git diff`, `git show`,
`git help`. Rather than scrolling past, Git pipes the output into a program that shows one screenful
at a time and waits for a keypress.

Both are chosen by a chain of settings, and both chains are documented in `git help var`, fetched from
<https://git-scm.com/docs/git-var> on 2026-08-23:

> **Editor:** *"The order of preference is `$GIT_EDITOR`, then `core.editor` configuration value, then
> `$VISUAL`, then `$EDITOR`, and then the default chosen at compile time, which is usually vi."*
>
> **Pager:** *"The order of preference is `$GIT_PAGER`, then the value of `core.pager` configuration,
> then `$PAGER`, and then the default chosen at compile time (usually less)."*

Two terms defined here, because they are used above:

- `$GIT_EDITOR` and `$PAGER` are **environment variables** — named values a program inherits from
  whatever started it. Day 1's part 3.1 explains them properly; today it is enough that they are set
  outside Git and Git reads them.
- `core.editor` and `core.pager` are **configuration settings**, in the files
  [2.1](../02-identity/2.1-config-and-scopes.md) took apart.

The chains have a shape worth noticing: an environment variable at the top for one command, then your
configuration, then the general-purpose environment variables that other Unix programs also honour,
then a compiled-in default. Day 1's parts 3.2 and 3.3 walk each chain link by link; this part sets
them and moves on.

## The mechanism

### Find out what Git will launch

```sh
git var GIT_EDITOR
git var GIT_PAGER
```

```
vim
less
```

**Line by line:**

- `git var` — ask Git for the value of one of its internal variables, resolved through the whole
  preference chain. It is the honest answer to "what will actually happen", as opposed to
  `git config --get core.editor`, which tells you only about one link in the chain.
- `vim` here because nothing else was set on this machine and that is what the installation nominated.
  On yours it might be `nano`, `notepad`, or an editor the installer configured.
- `less` is the pager on essentially every system this curriculum runs on.

### Make the editor yours

```sh
git config --global core.editor "nano"
git var GIT_EDITOR
```

```
nano
```

**Line by line:**

- `--global` — every repository, per [2.1](../02-identity/2.1-config-and-scopes.md).
- `nano` is the reasonable default for anybody who is not already fluent in a modal editor: arrow
  keys move, typing types, `Ctrl-O` saves, `Ctrl-X` exits, and the shortcuts are printed along the
  bottom of the screen.
- `git var` confirms it, which is the point of running the two commands together.

The common alternatives, and the flag that matters:

| Editor | Setting | Why the flag |
|---|---|---|
| nano | `git config --global core.editor "nano"` | No flag needed |
| VS Code | `git config --global core.editor "code --wait"` | **`--wait` is not optional.** Without it, `code` returns immediately, Git reads an empty file and aborts the commit |
| Vim | `git config --global core.editor "vim"` | Already the default on many systems |
| Notepad | `git config --global core.editor "notepad"` | Windows; blocks until closed, so no flag needed |

The `--wait` requirement is the single most common editor misconfiguration, and it produces the
`Aborting commit due to empty commit message.` failure in **When it breaks**, below — a graphical
editor that hands control straight back looks to Git exactly like an editor whose user saved nothing.

### If you are stuck in `vim` right now

Press `Esc`, then type `:wq` and press return — write and quit. To abandon instead: `Esc`, then `:q!`.
That is the whole survival kit, and it is worth knowing even if you never choose `vim`, because it is
the default on servers you will not have configured.

### What Git shows the editor

```sh
git commit
```

```
# Please enter the commit message for your changes. Lines starting
# with '#' will be ignored, and an empty message aborts the commit.
#
# On branch main
# Changes to be committed:
#	modified:   reminders.md
#
```

*(Captured with `GIT_EDITOR=cat`, which prints the file instead of editing it — a genuinely useful
trick for seeing what Git prepared.)*

**Line by line:**

- The blank first line is where your message goes. Everything below is a template.
- `Lines starting with '#' will be ignored` — the commented block is stripped before the message is
  stored, so you can read the file list while writing and leave it in place.
- `an empty message aborts the commit` — Git's own statement of the rule that catches the misconfigured
  graphical editor.
- `# Changes to be committed:` — the staged files, shown so you can check you are committing what you
  think. Day 18 is about writing the message itself, and `git commit -v` adds the entire diff below
  this block, which is the setting most professionals turn on permanently.

### Make the pager behave

The pager arrives with sensible defaults you did not set. From Git's own configuration documentation
(`Documentation/config/core.adoc` in Git's source, fetched 2026-08-23): when the `LESS` environment
variable is unset, Git sets it to `FRX`.

Those three letters are why Git's pager behaves differently from `less` on its own:

- **`F`** — quit immediately if the output fits on one screen. This is why a short `git log` does not
  trap you and a long one does.
- **`R`** — pass colour codes through rather than printing them as gibberish.
- **`X`** — do not clear the screen on exit, so the output stays in your scrollback.

Useful ways to change it:

```sh
git config --global core.pager "less -FRX -S"
```

**Line by line:**

- Setting `core.pager` explicitly overrides the default and lets you add flags.
- `-S` — do not wrap long lines; scroll sideways with the arrow keys instead. On wide diffs this is
  the difference between a readable column and a wall.
- Keep `F`, `R` and `X` when you override, or you will lose the three behaviours above without meaning
  to.

To skip the pager for one command:

```sh
git --no-pager log --oneline -5
git -c core.pager=cat log --oneline -5
```

**Line by line:**

- `--no-pager` — an option to `git` itself, so it goes *before* the subcommand. Useful when you want
  output in your scrollback rather than a full screen.
- `-c core.pager=cat` — the same effect through the configuration mechanism, and the form to use in a
  script where you want no surprises.
- Note that Git only pages when output goes to a terminal. `git log | grep water` never launches a
  pager, because the output is going to `grep` — which is why commands behave differently inside a
  script, and why Day 1's part 4.3 is about those streams.

### Keys that make the pager useful

| Key | What it does |
|---|---|
| `q` | Quit. **The answer to "the terminal is stuck"** |
| `Space` / `b` | Forward / back a screen |
| `/pattern` then `n` | Search forward, then next match |
| `g` / `G` | Top / bottom |
| `-S` then return | Toggle line wrapping, from inside the pager |

### A diff you can actually read

```sh
git diff
```

```
diff --git a/reminders.md b/reminders.md
index f8e0413..f6e309b 100644
--- a/reminders.md
+++ b/reminders.md
@@ -1,3 +1,3 @@
-water the plants
+water the plants twice
 call the dentist
 read a book
```

**Line by line:**

- `index f8e0413..f6e309b 100644` — the blob addresses before and after, and the file mode. Those are
  the content-addressed names from [1.1](../01-install/1.1-what-git-actually-is.md); Day 26 reads this header
  properly.
- `@@ -1,3 +1,3 @@` — the hunk header: from line 1, three lines, on each side.
- `-` and `+` — removed and added. Git shows a one-word change as a whole line replaced, because the
  unit of a diff is a line.

Which is exactly the readability problem, and there is a flag for it:

```sh
git diff --word-diff
```

```
diff --git a/reminders.md b/reminders.md
index f8e0413..f6e309b 100644
--- a/reminders.md
+++ b/reminders.md
@@ -1,3 +1,3 @@
water the plants {+twice+}
call the dentist
read a book
```

**Line by line:**

- `--word-diff` — compare word by word within changed lines. `{+…+}` marks an addition and `[-…-]` a
  removal.
- On prose, documentation and changelogs this is transformative; on code it is usually worse than the
  default. Day 26 covers when to reach for it.

And the flag that removes noise you did not create:

```sh
git diff --stat
git diff -w --stat
```

```
 reminders.md | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)
```
```
 reminders.md | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

**Line by line:**

- `--stat` — a summary rather than the content: which files, how many lines each way.
- `-w` — ignore whitespace-only differences. The first output counts two changed lines; the second
  counts one, because the extra change was only spacing. On a real review this is the difference
  between "forty files changed" and "two files changed and a formatter ran".
- Note both are *views* of the same commit. Nothing about the stored objects changes.

Two settings worth making permanent:

```sh
git config --global color.ui auto
git config --global diff.algorithm histogram
```

**Line by line:**

- `color.ui auto` — colour when the output is a terminal, plain text when it is piped. It is the
  default in current Git; setting it explicitly means a machine with an old system configuration
  behaves the same.
- `diff.algorithm histogram` — a different algorithm for deciding which lines correspond. On the
  three-line file above it makes no difference; on real code with moved blocks and repeated lines it
  produces noticeably more sensible hunks. Day 26 compares them on a file where the difference is
  obvious.

## The same thing, three ways

| Surface | Reading a change, and writing a message | Verdict |
|---|---|---|
| Terminal | `git diff` with `--word-diff`, `-w`, `--stat`; the editor for messages; the pager for anything long | **The one that works everywhere**, including on a server over SSH, and the only one that composes with other commands. |
| github.com | Renders diffs with syntax highlighting, side-by-side view, whitespace toggling and per-line comments; commit messages are written in a web textarea | **Genuinely better for reviewing somebody else's change** — Principle 15, the GUI is taught rather than sneered at. Worse for anything you need to script or repeat. |
| `gh` | `gh pr diff` prints a pull request's diff into your pager; `gh config set editor "code --wait"` sets the CLI's own editor for pull request and issue bodies | A third configuration for the same two programs, which is why [5.1](5.1-gh-auth-login.md) showed `editor=` empty in `gh config list` — empty means "fall back to the environment". |

**Which a professional reaches for:** the terminal while writing, the browser while reviewing. Reading
a colleague's forty-file change is faster with syntax highlighting and inline comments; checking your
own three-line change before committing is faster without leaving the keyboard. Knowing both means
choosing rather than defaulting.

## When it breaks

**The editor exits without producing a message.**

```
Aborting commit due to empty commit message.
```

*What it means:* Git launched the editor, the editor returned, and the file was empty or contained
only comment lines. Nothing was committed and the exit code is `1`. On a graphical editor this
usually means the launcher returned immediately — the `--wait` flag from the table above.

*Smallest fix:* `git config --global core.editor "code --wait"` for VS Code, or the equivalent flag
for your editor. Verify with `git var GIT_EDITOR`, then commit again — your staged changes are
untouched.

**The editor cannot run at all.**

```
error: there was a problem with the editor 'false'
Please supply the message using either -m or -F option.
```

*What it means:* Git launched the configured editor and it exited non-zero. `'false'` in the message
is the editor Git tried — read it, because it is frequently a typo or a path with a space in it that
was not quoted. Day 1's part 4.1 explains exit codes and why a non-zero one means "this failed".

*Smallest fix:* check `git var GIT_EDITOR`, correct `core.editor`, and quote the value if the path
contains spaces. As an immediate way round it, the message names one: `-m` for a one-line message, or
`-F <file>` to read the message from a file.

**The terminal appears frozen after a Git command.** Not an error, and the single most common
first-week experience.

```
(END)
```

*What it means:* the pager is showing the end of the output and waiting for you. Git has not hung and
nothing is broken.

*Smallest fix:* press `q`. If you want that to stop happening for short output, make sure `LESS` is
unset so Git can apply its own `FRX` default, or set `core.pager "less -FRX"` explicitly.

## In production

**Setting `core.editor` explicitly is a portability decision.** On a build agent or in a container
there may be no `EDITOR`, no `VISUAL`, and no `vi` — so any Git command that wants prose fails in a way
that looks unrelated. Scripts avoid the whole question by never invoking an editor: `-m` for messages,
`-F` for a file, and `GIT_SEQUENCE_EDITOR` set to a script for automated interactive rebases, which is
the trick behind Day 61's `--exec` work.

**Pagers break pipelines in a specific, memorable way.** A Git command whose output goes to a terminal
pages; the same command in a script does not, because standard output is not a terminal. That is
usually invisible — until a tool forces a pager on and a continuous-integration job hangs forever
waiting for a keypress nobody can press. `git --no-pager` in scripts, or the `GIT_PAGER=cat`
environment variable in a job, removes the class of failure entirely.

**Diff readability is a review-throughput problem.** A repository whose diffs are full of whitespace
churn gets reviewed less carefully, because the reviewer's attention is finite and is being spent on
noise. The mature answers are structural rather than personal: `.gitattributes` marking generated
files (Day 91), a formatter run by a hook so formatting changes never appear in feature commits
(Day 96), and `-w` in the reviewer's own habits. Day 26 covers `--diff-filter` and the rest of the
flags that turn a diff into a query.

**What a senior reviewer says.** On a pull request with a commit message consisting of one line
because the author always uses `-m`: *"put the *why* in the body — in six months the diff will still
be readable and your reasoning won't be."* That is a comment about an editor as much as about writing,
which is why this part comes before Day 18 rather than after.

**What it costs.** Nothing. Both programs are already installed.

**The interview question this is really testing.** *"Git opened an editor you didn't expect. What
happened, and how do you change it?"* The answer that lands names the chain rather than one setting:
Git needed prose, so it resolved an editor through `$GIT_EDITOR`, then `core.editor`, then `$VISUAL`,
then `$EDITOR`, then a compiled-in default — and `git var GIT_EDITOR` tells you which link won without
guessing.

## Check yourself

**Run this now.** Predict both answers before you press return, and say which link in each chain
supplied them:

```sh
git var GIT_EDITOR && git var GIT_PAGER
```

**Line by line:** `git var` resolves the full preference chain rather than reporting one setting, so
these are the programs that will actually launch. `&&` runs the second only if the first succeeds
(Day 1's part 4.2). If the editor is not one you can drive confidently, fix that now — the next part
of this day writes a commit message in it.

distinguishes the two possibilities, and give the single keystroke that resolves the likelier one.
