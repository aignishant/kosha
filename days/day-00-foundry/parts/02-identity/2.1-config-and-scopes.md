# 2.1 — `git config` and the four scopes

> **One-line answer.** Git's settings live in four plain text files — one for the machine, one for
> you, one for the repository, one for the worktree — and when two of them disagree the more specific
> file wins, which is why `--show-origin` is the only honest answer to "why is Git doing that?"

---

## The story

Two people at the same studio, the same afternoon, both convinced the other is doing something wrong.

Priya runs the command, and it does one thing. Deniz runs the same command on the same archive,
copied from the same place, and it does something noticeably different. They compare typing. The
typing is identical. They compare versions of the program — that is the sensible next check, and it
comes up equal. For twenty minutes each of them quietly suspects the other of having changed
something and forgotten.

Neither of them has. Priya's machine was set up by the studio's old laptop-imaging script, which
wrote a preference into a file neither of them has ever opened. Deniz's machine was set up by an
installer, three months later, which asked a question during setup and wrote a *different* preference
into a *different* file. Both machines are behaving exactly as configured. Neither person has ever
seen the configuration.

The lesson is not that settings exist. Everybody knows settings exist. The lesson is that there are
several files, they are consulted in a fixed order, and the tool will not volunteer which one it
listened to — unless you ask, in which case it will tell you precisely, and the argument ends in four
seconds.

---

## The idea in plain language

A **configuration** is a set of named values that change how a program behaves. Git's are all
`name = value` pairs, grouped into sections, stored in ordinary text files you can open in any
editor. There is no database and no registry.

The names have two parts, joined by a dot: `user.email` is the `email` setting in the `user` section.
Some have three, where the middle part is a subsection: `credential.https://dev.azure.com.useHttpPath`
configures credentials *for one host*. Section and setting names are case-insensitive — Git will store
`init.defaultBranch` and report it back to you as `init.defaultbranch`, which is not a corruption and
does not need fixing.

Git reads **four** of these files, in a fixed order, and later ones override earlier ones:

| Scope | The file | It applies to | Written with |
|---|---|---|---|
| **system** | Alongside the installation (`/etc/gitconfig`, or `…/Git/etc/gitconfig` on Windows) | Every user on this machine | `git config --system` (needs administrator rights) |
| **global** | `~/.gitconfig`, or `~/.config/git/config` | Every repository *you* touch on this machine | `git config --global` |
| **local** | `.git/config` inside the repository | This one repository | `git config --local` — the default when you write nothing |
| **worktree** | `.git/config.worktree` | One checked-out worktree of this repository | `git config --worktree`, and only when the repository opts in |

There is a fifth source that outranks all four: a value passed on the command line for one command
only, with `-c`. Git calls its scope `command`. It is the most useful debugging tool in this part,
because it lets you test a setting without saving it anywhere.

Two terms carried forward:

- `~` is the shell's shorthand for your home directory. It is expanded by the shell, not by Git —
  a distinction Day 1's part 1.3 makes concrete, and one that will bite you the first time you quote
  it by accident.
- A **worktree** is an additional working directory attached to the same repository, so you can have
  several branches checked out at once. Day 40 builds them; today the word only needs to be a word.

### The rule, in one sentence

**Read all four in order — system, global, local, worktree — and the last value found wins.**

That is Git's documented behaviour, from the FILES section of `git help config`, fetched from
<https://git-scm.com/docs/git-config> on 2026-08-23: *"The files are read in the order given above,
with last value found taking precedence over values read earlier."*

## Why the build needs it

**The very next part** sets your name and email address. If you set them in the wrong scope, every
repository you clone afterwards is silently attributed to nobody, and
[2.2](2.2-identity-in-every-commit.md) explains why that is expensive to fix later rather than merely
untidy.

**Day 99** gives you a different identity per directory — work commits signed with the work address,
personal commits with the personal one — using conditional includes. That whole mechanism is an
extension of the precedence chain in this part, and it is incomprehensible without it.

**Day 155 onward**, when a workflow runs Git inside a continuous-integration job, the job has no
global configuration at all: a fresh container, a fresh home directory, nothing set. Every setting the
job needs must be set explicitly, and knowing which scope to write it in is the difference between a
workflow that works and one that works on your laptop.

## The mechanism

### Ask Git what it is reading, and from where

```sh
git config --global --list --show-origin --show-scope
```

```
global	file:C:/kosha-demo/home/.gitconfig	user.name=Priya Raman
global	file:C:/kosha-demo/home/.gitconfig	user.email=priya@example.com
```

**Line by line:**

- `--global` — restrict this listing to the global file. Without it you get every scope at once, which
  is usually what you want and is shown in a moment.
- `--list` — print every setting rather than asking for one.
- `--show-origin` — prefix each line with the *file* it came from. This is the flag that ends
  arguments.
- `--show-scope` — prefix each line with the scope name: `system`, `global`, `local`, `worktree` or
  `command`.
- The path here is from a demonstration home directory; yours will read `…/.gitconfig` under your own
  home. The columns are separated by tab characters, which matters if you ever pipe this into another
  program.

### The file is just text

```sh
cat ~/.gitconfig
```

```
[user]
	name = Priya Raman
	email = priya@example.com
```

**Line by line:**

- `cat` — print a file to the screen. Nothing Git-specific is happening; this is an ordinary text
  file.
- `[user]` — a section header. Everything indented under it belongs to that section, so
  `name = Priya Raman` is the setting `user.name`.
- The indentation is a tab, and Git writes it that way itself. You may edit this file by hand — Git
  re-reads it every time — and `git config --global --edit` opens it in your editor for exactly that
  purpose.

### Watch a more specific scope win

```sh
git config user.email "priya@studio.example"
git config --list --show-scope | grep -E '^(global|local)\s+user\.'
```

```
global	user.name=Priya Raman
global	user.email=priya@example.com
local	user.email=priya@studio.example
```

**Line by line:**

- `git config user.email "…"` — with no scope flag, Git writes to the **local** file. This is the
  single most common surprise in this part: the default for *writing* is local, while the default for
  *reading* is all four.
- `--list --show-scope` — every setting from every scope, labelled.
- `grep -E '^(global|local)\s+user\.'` — keep only the global and local lines about `user.`. `\s+`
  matches the tab between columns.
- Both values are still there. Nothing was overwritten. Two files each hold a `user.email`, and the
  question is only which one Git uses.

```sh
git config user.email
git config --show-origin --get user.email
```

```
priya@studio.example
file:.git/config	priya@studio.example
```

**Line by line:**

- The first command asks for the effective value — the winner — and gets the local one.
- `--get` — return a single value rather than a list. With `--show-origin` it also names the file, and
  `file:.git/config` is a relative path because that file is inside the repository you are standing
  in.
- `--get-all` is the variant you need when a setting may legitimately appear more than once, which
  some can.

### The fifth source: one command, one value

```sh
git -c user.email=deniz@example.com config --show-scope --get user.email
```

```
command	deniz@example.com
```

**Line by line:**

- `-c name=value` — set a configuration value for **this invocation only**. Note where it sits: before
  the subcommand, because it is an option to `git` itself, not to `config`.
- Nothing is written to any file. The next command sees the old value again.
- This is how you test a theory safely: `git -c core.pager=cat log` answers "is my pager the problem?"
  without changing anything, and how a script guarantees a setting regardless of the machine it runs
  on.

### What the machine already decided for you

Most people believe they have configured nothing at the start. On Windows in particular, they are
wrong:

```sh
git config list --show-scope | head -13
```

```
system	diff.astextplain.textconv=astextplain
system	filter.lfs.clean=git-lfs clean -- %f
system	filter.lfs.smudge=git-lfs smudge -- %f
system	filter.lfs.process=git-lfs filter-process
system	filter.lfs.required=true
system	http.sslbackend=schannel
system	core.autocrlf=true
system	core.fscache=true
system	core.symlinks=true
system	pull.rebase=false
system	credential.helper=manager
system	credential.https://dev.azure.com.usehttppath=true
system	init.defaultbranch=master
```

**Line by line:**

- `git config list` — the modern subcommand spelling of `git config --list`. Git 2.46 added
  `git config get|set|unset|list` alongside the older flag forms, and both work; the subcommand form
  is clearer to read in scripts and is what newer documentation uses.
- Every one of these lines was written by the installer, into the system file, before you typed
  anything. Three of them will change your life today:
  - `core.autocrlf=true` rewrites line endings in every file that crosses between your disk and the
    object store. [2.3](2.3-defaults-worth-changing.md) shows the rewriting byte by byte.
  - `credential.helper=manager` decides where your GitHub credentials are stored.
    [4.4](../04-auth/4.4-credential-helpers.md) opens that store.
  - `init.defaultbranch=master` names the first branch of every repository you create.
    [2.3](2.3-defaults-worth-changing.md) changes it.
- If you have ever wondered why "Git out of the box" behaves differently for two people, this listing
  is the answer, and it is why `--show-origin` beats reasoning about it.

### Writing and removing

```sh
git config set --local user.email "priya@studio.example"
git config get user.email
git config unset --local user.email
git config get user.email
```

```
priya@studio.example
priya@example.com
```

**Line by line:**

- `git config set --local …` — write to the repository's own file. Explicit scope, even though local
  is the default, because a reader of your script should not have to know the default.
- `git config get user.email` — read the effective value. After the local one is set, it wins.
- `git config unset --local user.email` — delete that one line from the local file. It does not set it
  to empty; the setting ceases to exist in that scope.
- The second `get` returns the global value again. **Removing a setting does not remove the behaviour
  — it uncovers whatever the next scope up says**, which is a distinction that matters the first time
  you "turn off" something and it stays on because the system file also sets it.

## The same thing, three ways

| Surface | Reading and writing Git's own settings | Verdict |
|---|---|---|
| Terminal | `git config list --show-scope --show-origin`, `git config get`, `git config set`, `git config --edit` | **The only complete surface.** Every scope, every value, and the file each came from. |
| github.com | Cannot see your local Git configuration at all — it is on your machine and never transmitted. The website has its own settings (default branch name for new repositories, merge button options), which are *GitHub's* configuration and land in a different place | The two are genuinely different systems. A repository's default branch on GitHub and your `init.defaultBranch` both matter, and neither one sets the other. |
| `gh` | `gh config list` and `gh config set` manage the **CLI's** settings — editor, pager, git protocol — in `~/.config/gh/config.yml`, a separate file in a different format | Three configuration systems on one machine. Knowing which tool owns a setting is most of the skill. |

**Which a professional reaches for:** `git config --show-origin` the moment behaviour surprises them,
before forming any theory at all. The habit is worth more than the knowledge: the reflex of *asking
the tool where a value came from* rather than reasoning about where it might have come from is the
whole of debugging configuration.

## When it breaks

**Asking for a setting that is not set.**

```sh
git config get help.format
```

```
```

*What it means:* nothing printed, and the command exited with status `1`. Git distinguishes "the value
is empty" from "there is no such value", and reports the second as a failure exit code with no output.
This is why `if git config get some.key >/dev/null; then …` is the correct way for a script to ask
"is this configured?" — Day 1's part 4.1 is about reading exit codes deliberately.

*Smallest fix:* none needed; this is normal. If you expected a value, check the scope you looked in —
`git config get --global …` reads only the global file and will report "not set" for something that is
set locally.

**A value Git cannot interpret.** Setting is not validating: Git accepts the write and complains
later, when something needs the value.

```
fatal: invalid value for 'pull.rebase': 'notabool'
```

*What it means:* `pull.rebase` must be a boolean (`true`, `false`) or `interactive`/`merges`, and
`notabool` is none of those. The write succeeded; the *use* failed. Note that the error arrives during
a completely different command from the one that caused it, which is why the setting's name is in the
message and why you should read it.

*Smallest fix:* `git config unset --global pull.rebase`, then set it correctly. You can also ask Git
to check a stored value against a type before you depend on it:

```sh
git config --type=bool --get pull.rebase
```

```
fatal: bad boolean config value 'notabool' for 'pull.rebase'
```

**Line by line:** `--type=bool` tells Git to interpret the stored string as a boolean and normalise it
to `true` or `false`. When it cannot, you get the failure now, in a command you chose to run, instead
of during a `git pull` in the middle of something else.

**Editing the file with the wrong syntax.** If you hand-edit `~/.gitconfig` and unbalance a section
header, every Git command in every repository starts failing at once:

```
fatal: bad config line 1 in file C:/kosha-demo/home/.gitconfig
```

*What it means:* Git cannot parse the file, so it refuses to run rather than run with half a
configuration. The message names the file and the line, which is all you need.

*Smallest fix:* open that file at that line and repair it. This failure is loud, immediate and total,
which is the good kind — and it is why hand-editing is safe: you find out instantly.

## In production

**Configuration precedence is how organisations enforce policy without trusting memory.** A machine
image sets the system file; a dotfiles repository sets the global one; a repository ships its own
expectations in a committed file that developers include from their global config with `include.path`.
Day 89 builds that arrangement properly, and Day 100's gate is a repository that configures every
clone of itself.

**In continuous integration, every scope you rely on is missing.** A workflow runner starts with an
empty home directory. Anything a script needs — `user.email` to make a commit, `safe.directory` for a
repository owned by a different user, a credential helper — must be set inside the job. This is the
single most common reason a script that works on a laptop fails in a pipeline, and the fix is either
`git -c …` per command or an explicit `git config --global` step at the top of the job.

**What a senior reviewer says.** On a pull request adding a setup script that runs
`git config --global core.autocrlf false`: *"don't write to the developer's global config from a
project script — put it in `.gitattributes` so it applies to this repository for everyone, including
the people who never run your script."* Choosing the narrowest scope that achieves the goal is the
professional instinct, and Day 91 is about the file that does it properly.

**What it costs.** Nothing but disk bytes. `git config` is local, offline and instant even on a
repository with a million commits, because it reads four small text files and nothing else.

**The interview question this is really testing.** *"A colleague says Git is doing something strange
on their machine. What do you ask them to run first?"* The answer is `git config --show-origin --get
<the-setting>`, or `--list --show-origin` if the setting is not yet known — and the reason: settings
live in four files with a defined precedence, and knowing *which file* is the whole diagnosis.

## Check yourself

**Run this now.** Predict, before you press return, whether you will see zero, one, or several lines —
and which scope will be at the front of each:

```sh
git config --list --show-scope --show-origin | grep -i autocrlf
```

**Line by line:** `--list --show-scope --show-origin` prints every setting from every scope with its
label and file; `grep -i autocrlf` keeps only the line-ending setting, case-insensitively. On Windows
you will see a `system` line you never wrote. On Linux or macOS you may see nothing at all, which is a
different default and equally worth knowing about your own machine.

**Say this out loud.** You set `user.email` this morning and a commit you made this afternoon still
has the wrong address on it. Name the three places the value could have come from, and the one command
that tells you which.
