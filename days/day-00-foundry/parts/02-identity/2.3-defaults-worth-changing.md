# 2.3 — The defaults you will regret leaving alone

> **One-line answer.** Git's defaults are chosen so that a repository from 2005 still works and no
> existing script breaks, which is not the same as being chosen for you — six of them are worth
> changing on your first day and then never thinking about again.

---

## The story

A studio buys a second-hand van. It runs, the doors close, and it gets everyone to the shoot.

Six months later somebody notices that the wing mirror has been adjusted for a driver who is not
there any more, that the seat is bolted a notch too far back, and that the radio is tuned to a station
nobody likes. None of it stopped the van from working. Nobody had a bad day because of the mirror.
Everybody made a small unconscious adjustment, every single journey, for six months.

Software defaults are the same, with one difference that matters: they were not left by a previous
driver, they were chosen by people who could not know who would end up driving. A default has to be
safe for a repository created twenty years ago, for a script written by somebody who has retired, and
for a person who has never heard of the setting. That is a genuinely hard constraint, and the result
is a set of choices that are defensible for everybody and optimal for nobody.

You are about to spend two hundred and fifty days in this van. Adjust the mirror.

---

## The idea in plain language

Every setting in this part follows the same shape: Git chose a behaviour, the behaviour has costs, and
those costs land on *you* rather than on the project that needed compatibility. Changing them is
`git config --global`, which [2.1](2.1-config-and-scopes.md) explained.

Three terms are used below and defined here, so this part can be read cold:

- A **branch** is a named pointer to a commit. Creating one is nearly free, and Day 33 shows exactly
  what `git branch` writes to disk. Today the word only needs to mean "the name of a line of work".
- An **upstream** is the remote branch your local branch is paired with, so that `git push` and
  `git pull` know where to go without being told. Day 36 builds them properly.
- A **fast-forward** is the case where your branch has no commits the other one lacks, so bringing it
  up to date means only sliding the pointer forward — no merge, no new commit, no possibility of
  conflict. Day 42 is the full treatment.

### The six

| Setting | Default | Change to | Why |
|---|---|---|---|
| `init.defaultBranch` | `master` | `main` | The name your repositories are born with, and the one GitHub expects |
| `core.autocrlf` (Windows) | `true` | `false`, plus `.gitattributes` | It silently rewrites bytes on the way in and out |
| `pull.ff` | unset — Git refuses and asks | `only` | Turns a surprise merge commit into a question you answer deliberately |
| `push.autoSetupRemote` | `false` | `true` | Removes the "no upstream branch" ritual from every new branch |
| `fetch.prune` | `false` | `true` | Stops deleted remote branches lingering in your clone forever |
| `merge.conflictStyle` | `merge` | `zdiff3` | Puts the common ancestor inside the conflict markers, so you can see what each side changed |

Two more that belong in the same breath and are covered elsewhere:
`user.useConfigOnly true`, argued for in [2.2](2.2-identity-in-every-commit.md), and `core.editor`,
which [5.2](../05-cli-tools/5.2-editor-and-pager.md) sets after showing you what it does.

## Why the build needs it

**Day 46** teaches conflict resolution using the ancestor shown inside the conflict markers. With the
default conflict style there is no ancestor in the markers, and the day's central technique — compare
each side to what was there before — is not available.

**Day 80** is `git push` in full. Every branch you create between now and then would otherwise open
with the same eight-line refusal, and you would learn to type a command by rote instead of
understanding upstreams.

**Day 92** is an entire day about line endings, and it exists because `core.autocrlf` on Windows makes
two developers' checkouts differ byte for byte while both `git status` outputs say "clean". Setting it
correctly today means that day is a lesson rather than a rescue.

**Day 79** is `git pull`, and its subtitle in the plan is "why the default bites". The setting in this
part is the bite, defused early.

## The mechanism

### 1. `init.defaultBranch` — the name your repositories are born with

Create a repository with nothing configured and Git tells you, at length, that it has made a choice
for you:

```sh
git init
```

```
hint: Using 'master' as the name for the initial branch. This default branch name
hint: will change to "main" in Git 3.0. To configure the initial branch name
hint: to use in all of your new repositories, which will suppress this warning,
hint: call:
hint:
hint: 	git config --global init.defaultBranch <name>
hint:
hint: Names commonly chosen instead of 'master' are 'main', 'trunk' and
hint: 'development'. The just-created branch can be renamed via this command:
hint:
hint: 	git branch -m <name>
hint:
hint: Disable this message with "git config set advice.defaultBranchName false"
Initialized empty Git repository in C:/kosha-demo/hint/.git/
```

**Line by line:**

- `git init` — create a repository in the current directory. It printed a `hint:` block because
  nothing has told it what to name the first branch.
- **"will change to "main" in Git 3.0"** — this is Git's own announcement, printed by the version on
  this machine today. The default is moving; setting it explicitly means your machine behaves the same
  before and after that release.
- `advice.defaultBranchName false` would silence the message without deciding anything. Silencing a
  question instead of answering it is how you end up with repositories whose first branch name depends
  on which year you created them.

```sh
git config --global init.defaultBranch main
```

**Line by line:** every repository you create from now on starts on `main`. This changes nothing about
existing repositories, and nothing about repositories you clone — a clone gets whatever the origin
has.

### 2. `core.autocrlf` — the setting that edits your files

This one is Windows-specific and it is the most consequential item on the page, because it changes
bytes without telling you.

```sh
git config --show-origin --get core.autocrlf
```

```
file:C:/Program Files/Git/etc/gitconfig	true
```

**Line by line:** the value is `true`, and it came from the **system** file — the installer wrote it,
not you. [2.1](2.1-config-and-scopes.md) is the part that lets you find that out in one line.

Watch what `true` does. Here is a file written with Unix line endings, added to a repository:

```sh
printf 'water the plants\ncall the dentist\n' > reminders.md
git add reminders.md
```

```
warning: in the working copy of 'reminders.md', LF will be replaced by CRLF the next time Git touches it
```

**Line by line:**

- `printf` writes exactly the bytes given: two lines, each ending with a single newline character
  (`\n`, also called LF).
- The warning is Git telling you, in advance, that it intends to rewrite your working file.

Now compare what is on disk with what went into the object store:

```sh
od -c reminders.md | head -3
git cat-file -p :reminders.md | od -c | head -3
```

```
0000000   w   a   t   e   r       t   h   e       p   l   a   n   t   s
0000020  \n   c   a   l   l       t   h   e       d   e   n   t   i   s
0000040   t  \n
```
```
0000000   w   a   t   e   r       t   h   e       p   l   a   n   t   s
0000020  \n   c   a   l   l       t   h   e       d   e   n   t   i   s
0000040   t  \n
```

**Line by line:**

- `od -c` — dump a file byte by byte, showing control characters by name. `\n` is a line feed; `\r`
  will appear in a moment and is a carriage return.
- `git cat-file -p :reminders.md` — print the content **as stored**. The `:path` syntax means "the
  version of this path in the index" — Day 13 introduces the index properly; Day 24 covers this
  syntax as a language.
- Both are `\n` only, so far. The object store holds LF, which is what you want: the repository is the
  same on every platform.

Now let Git write the file out again, which is what happens on every checkout, switch and clone:

```sh
git commit -qm "two reminders"
rm reminders.md
git restore reminders.md
od -c reminders.md | head -3
```

```
0000000   w   a   t   e   r       t   h   e       p   l   a   n   t   s
0000020  \r  \n   c   a   l   l       t   h   e       d   e   n   t   i
0000040   s   t  \r  \n
```

**Line by line:**

- `git restore reminders.md` — write the committed version back into the working tree. Day 19 is about
  this command.
- Every `\n` is now `\r \n`. **Your file on disk is not the file in the repository, byte for byte.**

And the part that makes it hard to notice:

```sh
git status --short
```

```
```

**Line by line:** empty output — the working tree is reported clean, because Git converts back when it
compares. The conversion is consistent, so it hides. It stops hiding the day a tool that is not Git
reads those files: a shell script with `\r` at the end of its first line fails with a message about a
command that does not exist, and a checksum computed on Windows disagrees with the same checksum
computed in a container.

```sh
git config --global core.autocrlf false
```

**Line by line:** stop converting. Store what I wrote, check out what was stored. The complete
professional answer is to leave conversion to a `.gitattributes` file committed *in the repository*,
so that the policy travels with the project instead of depending on each contributor's machine —
that file is Day 91, and Day 92 is the full incident. Turning the machine-wide rewriting off today is
the half you can do now, and it is the half that prevents surprises.

### 3. `pull.ff` — make the surprise into a question

With nothing configured, Git refuses to pull when the two branches have diverged, and explains itself:

```
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.
```

**Line by line:**

- **"divergent"** means both sides have commits the other does not. There is no way to combine them
  without either a merge commit or a replay.
- Git is asking you to choose a policy in advance, which is the right question — but note the trap:
  the Windows installer already answered it for you, writing `pull.rebase=false` into the system file,
  which silently chooses *merge* and means you never see this message.

Choose `only`:

```sh
git config --global pull.ff only
```

Then the divergent case fails instead of quietly making a merge commit:

```
hint: Diverging branches can't be fast-forwarded, you need to either:
hint:
hint: 	git merge --no-ff
hint:
hint: or:
hint:
hint: 	git rebase
hint:
hint: Disable this message with "git config set advice.diverging false"
fatal: Not possible to fast-forward, aborting.
```

**Line by line:**

- `pull.ff only` — pull is allowed to fast-forward and nothing else. If the histories have diverged,
  stop and let the human decide.
- Nothing was lost and nothing was created. You are exactly where you were, holding a decision instead
  of a merge commit you did not intend. Day 79 is where that decision gets its full treatment.

### 4. `push.autoSetupRemote` — stop typing the ritual

```sh
git switch -c feature
git commit -qam "add stretch"
git push
```

```
fatal: The current branch feature has no upstream branch.
To push the current branch and set the remote as upstream, use

    git push --set-upstream origin feature

To have this happen automatically for branches without a tracking
upstream, see 'push.autoSetupRemote' in 'git help config'.
```

**Line by line:**

- Git will not guess where a new branch belongs, because in a repository with several remotes the
  guess could publish your work to the wrong place.
- The message names the setting that changes the policy — Git telling you how to stop being asked.

```sh
git config --global push.autoSetupRemote true
git push
```

```
To C:/kosha-demo/up
 * [new branch]      feature -> feature
branch 'feature' set up to track 'origin/feature'.
```

**Line by line:**

- `* [new branch] feature -> feature` — the branch was created on the remote.
- `branch 'feature' set up to track 'origin/feature'` — the upstream was recorded, so future
  `git push` and `git pull` on this branch need no arguments. Day 36 is about that pairing and Day 80
  about the push itself.
- Needs Git 2.37 or newer; [1.2](../01-install/1.2-installing-git.md) has the version table.

### 5. `fetch.prune` — stop collecting ghosts

A colleague deletes a branch on the remote after it is merged. Your clone does not notice:

```sh
git fetch
git branch -r
```

```
  origin/HEAD -> origin/main
  origin/feature
  origin/main
```

**Line by line:**

- `git branch -r` — list *remote-tracking* branches: your local record of where each branch was on the
  remote, last time you looked. Day 76 is entirely about the difference between `origin/main` and
  `main`, and it is a difference worth taking seriously.
- `origin/feature` is still listed. It does not exist on the remote any more. Nothing will ever remove
  it on its own.

```sh
git fetch --prune
git branch -r
```

```
  origin/HEAD -> origin/main
  origin/main
```

**Line by line:**

- `--prune` — delete remote-tracking references whose branches are gone from the remote. It touches
  only your local record of *their* branches; your own branches and your commits are not involved.

```sh
git config --global fetch.prune true
```

**Line by line:** do that every time, so a two-year-old clone shows the branches that exist rather
than every branch that ever existed. On a busy repository this is the difference between a
completion list with twelve entries and one with four hundred.

### 6. `merge.conflictStyle` — see what the ancestor said

```sh
git config --global merge.conflictStyle zdiff3
```

**Line by line:**

- The default style shows you two versions in the conflict markers: yours and theirs. `zdiff3` shows
  three — yours, theirs, and **what was there before either of you touched it**.
- Without the third, resolving a conflict means guessing which side changed what. With it, you can
  see it. Day 45 reads conflict markers and Day 46 is this setting in full, with the markers side by
  side.
- Needs Git 2.35 or newer. On an older Git, `diff3` is the same idea without the tidying `z` does.

### All six, as a block

```sh
git config --global init.defaultBranch main
git config --global core.autocrlf false
git config --global pull.ff only
git config --global push.autoSetupRemote true
git config --global fetch.prune true
git config --global merge.conflictStyle zdiff3
```

**Line by line:** six writes to one file, `~/.gitconfig`. Nothing here touches a repository, nothing
is destructive, and every one of them is reversible with `git config --global unset <name>` — which,
as [2.1](2.1-config-and-scopes.md) showed, uncovers whatever the system file says rather than
returning to some abstract "default".

Check what you have written:

```sh
git config --global --list
```

```
user.name=Priya Raman
user.email=priya@example.com
init.defaultbranch=main
pull.rebase=true
push.autosetupremote=true
fetch.prune=true
merge.conflictstyle=zdiff3
rerere.enabled=true
```

**Line by line:** the names come back lowercased, which is Git normalising them and not a mistake.
This listing is from a machine that also enabled `rerere` (Day 49 — Git remembering how you resolved
a conflict so it can replay the resolution next time) and chose `pull.rebase` rather than `pull.ff`,
which is the other defensible answer to §3 and the one Day 79 argues about.

## The same thing, three ways

| Surface | Choosing defaults | Verdict |
|---|---|---|
| Terminal | `git config --global …` writes `~/.gitconfig`; `--list --show-origin` proves what took effect | **Where your machine's behaviour is decided.** All six settings in this part live here and nowhere else. |
| github.com | Owns a different set of defaults for the *server* side: the default branch name for new repositories (Settings → Repositories → Repository default branch), whether merge commits or squashing are allowed, whether branches are deleted automatically after merge | These are the same *questions* as `init.defaultBranch` and `pull.ff`, answered for the organisation rather than for your laptop. Neither location sets the other, and both matter. |
| `gh` | `gh repo create` inherits GitHub's server-side default branch, not your `init.defaultBranch`; `gh config set git_protocol ssh` sets the CLI's own preference | A third configuration system, as [2.1](2.1-config-and-scopes.md) warned. When a new repository comes back on the wrong branch name, this is why. |

**Which a professional reaches for:** the terminal for their own machine, and the organisation's
settings page for anything that must be true for everybody — because a policy that depends on each
person having run six commands is not a policy. Day 100's gate is exactly that: a repository that
configures every clone of itself.

## When it breaks

**A checksum computed on your machine disagrees with everyone else's.**

```sh
printf 'water\n' | sha1sum
printf 'water\r\n' | sha1sum
```

```
234b79a27ec77cbd3380c1feec34fadc3d5b22ec *-
2300de2c6c8ead36f0550fba0d71196653088f98 *-
```

**Line by line:** the same five characters, differing only in the line ending, hash to two unrelated
values — the property [1.1](../01-install/1.1-what-git-actually-is.md) established. If your checkout has been
converted to CRLF and a container's checkout has not, every hash, every signature and every
byte-comparison over those files disagrees, while both `git status` outputs say the tree is clean. No
error message announces this; you find it in a failing verification step.

*Smallest fix:* `git config --global core.autocrlf false`, then re-check out the affected files in a
repository you are willing to reset — or, properly, commit a `.gitattributes` marking the file
`text eol=lf`, which is Day 91 and is the only fix that also applies to your colleagues.

*A related failure, not reproducible on this machine:* on systems whose shell does not tolerate a
carriage return, a converted shell script fails at its first line with a message naming `$'\r'` as an
unknown command. The shell shipped with Git for Windows tolerates it, so the exact text is not pasted
here — `TODO(verify)` on a Linux machine if you want it verbatim. The underlying cause is the same
conversion.

**A pull that used to work starts refusing.**

```
fatal: Not possible to fast-forward, aborting.
```

*What it means:* `pull.ff only` is doing its job. Your branch and the remote branch have both moved.

*Smallest fix:* decide. `git pull --rebase` to replay your commits on top of theirs, or `git merge
origin/main` to make the merge commit deliberately. Day 79 argues the choice properly; the point of
the setting is that you now make it on purpose.

**`git config --global` fails with no home directory.**

```
fatal: $HOME not set
```

*What it means:* the global scope is defined as a file inside your home directory, and there isn't
one. This happens in containers and on build agents, not on laptops.

*Smallest fix:* set `HOME`, or write the settings with `git -c name=value` per command, which needs no
file at all. This is the situation described in [2.1](2.1-config-and-scopes.md)'s production section,
and it is why continuous-integration scripts configure Git explicitly at the top of the job.

## In production

**Nobody sets these by hand twice.** The professional pattern is a **dotfiles repository**: a
repository holding your `~/.gitconfig`, your shell configuration and your editor settings, so a new
machine is one clone and one symlink from being yours. That repository is itself version-controlled,
which means you can see when you changed a setting and why — and it is the reason a senior engineer's
new laptop is productive in an hour instead of a fortnight of small irritations.

**Team-wide settings do not belong in anyone's home directory.** Line-ending policy belongs in a
committed `.gitattributes` (Day 91), hook policy in `core.hooksPath` pointing at a committed directory
(Day 97), and merge behaviour for a particular file in a merge driver (Day 50). The rule of thumb:
**if it must be true for everyone who clones the repository, it goes in the repository.** A setting
that lives only in your global config is a setting that is false for every new contributor.

**Defaults change, and reading the release notes is part of the job.** The `init.defaultBranch` hint
on this page announces a change coming in Git 3.0. `merge.conflictStyle zdiff3` did not exist before
2.35. `push.autoSetupRemote` did not exist before 2.37. A team that pins Git versions (Day 237's cost
work has the same flavour) reads what changed before upgrading, because a changed default is a changed
behaviour on every machine at once.

**What a senior reviewer says.** On a pull request where half the lines of a file appear changed but
the diff shows nothing meaningful: *"this is a line-ending flip — fix `core.autocrlf`, add the file to
`.gitattributes`, and re-push, because right now this diff is unreviewable."* Ninety per cent of
"whole file changed" pull requests are this, and it is why the setting is on this page rather than in
Day 92 alone.

**What it costs.** Nothing. Six lines in one text file.

**The interview question this is really testing.** *"Which Git settings do you change on a new
machine, and why?"* It is a proxy for how much time you have spent with the tool. A strong answer
names two or three and gives the failure each one prevents — the line-ending rewrite that makes a diff
unreviewable, the accidental merge commit from a default `pull`, the stale remote branches nobody ever
prunes. The reasons are the answer; the list is just the evidence.

## Check yourself

**Run this now.** Predict the number before you run it — how many of the six have you actually
written?

```sh
git config --global --list | grep -cE '^(init\.defaultbranch|core\.autocrlf|pull\.(ff|rebase)|push\.autosetupremote|fetch\.prune|merge\.conflictstyle)='
```

**Line by line:** `--global --list` prints only your own file, so system settings do not inflate the
count; `grep -cE` counts lines matching any of the six names, anchored with `^` and `=` so that only
whole setting names match. If the answer is smaller than you expected, the missing ones are probably
being supplied by the system file — `--show-origin` will confirm it.

**Say this out loud.** Explain to a colleague why `core.autocrlf true` can make `git status` say
"clean" while their file on disk differs, byte for byte, from the file in the repository — and say
which of the two Git considers authoritative.
